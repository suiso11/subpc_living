## 背景

現在のテストは `unittest` スタイルの `TestCase` と、テスト内で `patch()` や一時ディレクトリ、
Fakeクラス、小さなヘルパー関数を組み合わせてテストデータを組み立てている。
一方 `pyproject.toml` には `[tool.pytest.ini_options]`（`pythonpath` / `testpaths`）も存在し、
pytest によるテスト発見が可能な構成になっている。実行・発見手段は混在しているが、
テストコード本体は unittest ベースで、専用のテストファクトリライブラリは未導入。

## 現時点の決定

thoughtbot/fishery は今は追加しない。
代わりに、小さな Python テストファクトリ/ヘルパー（関数や軽量ビルダー）をまず導入する。
既存のテストファクトリへの全面リファクタは未実施であり、実施予定も現時点ではない。

## 判断理由

- 現在のテスト層は Python が中心で、fishery の主対象である TypeScript エコシステムとは
  一致しない。
- 導入コストに対し、既存の unittest + 小ヘルパー構成で足りている領域が大半。
- テストデータ構築の重複が増えて実害が出るまでは、追加依存を増やさない方針。

## 段階的導入計画

1. テスト内で重複しているデータ構築を、`tests/` 配下の小さなファクトリ/ヘルパー関数に寄せる。
2. 利用頻度の高い型（config・DBレコード・メッセージ等）から順に対象を広げる。
3. 必要になった時点で、Python 向けの本格的なテストファクトリライブラリを再評価する。

## fishery を再検討する条件

- TypeScript フロントエンドが導入され、JS テストランナー（Jest / Vitest 等）が加わった場合。
- その際、fishery が現在のテストスタイルと実害（重複・メンテナンス負荷）に対して
  明確な改善をもたらすと判断できた場合。
